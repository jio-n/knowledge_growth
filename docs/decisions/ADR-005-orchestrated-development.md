# ADR-005: 設計文書先行 + オーケストレーション開発方式

日付: 2026-07-11 / 状態: 採用(ユーザー指示による)

## 文脈
§23/§24: Fable 5のセッションが失われても、人間・Claude Code・Codex・他のLLMが開発を継続できること。またユーザーはトークンコスト効率を要望(2026-07-11の指示)。

## 決定
1. **docs/ を正本とする**。実装より先に設計文書(要件・データモデル・API契約・UI仕様・アンカー仕様・AI処理フロー)をコミットし、以後の実装はすべて文書に対して行う。文書と実装が食い違ったら文書を直すか実装を直すかを明示的に判断し、必ず同期させる。
2. **オーケストレーション**: 高コストモデル(Fable 5等)は設計・仕様策定・レビュー・統合・難所(アンカー解決等)のみを担当。仕様が固まった自己完結モジュールは、より安価なモデル(Sonnet等)のサブエージェントに委譲する。
3. サブエージェントへの発注は会話コンテキストではなく**コミット済み文書パスの参照**で行う(例:「docs/product/ui_spec.md と docs/architecture/api_spec.md に従い client/ を実装せよ」)。これにより発注内容自体が再現可能な成果物になる。
4. 小さい単位で頻繁に git commit し、任意時点で中断・再開可能に保つ。

## 帰結
- 文書がやや冗長になるが、それ自体が引き継ぎ資産(§31)。
- サブエージェント成果物はオーケストレーターがレビュー・修正してからコミットする(品質担保)。
