# 改善提案一覧(§27)

最終更新: 2026-07-11。採否の最終判断者はユーザー。「採用済」はMVP実装に反映済みの判断(理由と共に記録)。

## A. MVPに採用(実装へ反映済み)

### A-1. オフラインモックLLMプロバイダーを一級市民にする
- 解決する問題: APIキー・ネットワーク・コストが無いと開発もテストもデモもできない
- 現在の要件との差分: 要件はプロバイダー交換可能性のみ言及。「キーなしで全フロー動作」は追加提案
- 提案する体験: 初回起動で必ず動く。モック回答は明示ラベル付きで誤認不可
- 期待効果: テスト自動化、コストゼロの開発、E2E完了条件(§30)の検証可能性
- 実装コスト: 小 / 技術的リスク: なし / MVP適合性: 高
- 推奨判断: **採用済**(ADR-003)

### A-2. W3C TextQuote型の冗長アンカー
- 解決する問題: 単一方式(位置番号のみ等)のアンカーは再解析・ページ更新で全滅する
- 差分: 要件は複数アンカー候補を列挙するのみ。blockId(速い)+quote/prefix/suffix(頑健)の併用と5段階フォールバック解決を仕様化
- 期待効果: Web更新耐性(§27の観点)、リンク切れでも知識は保全
- コスト: 中 / リスク: 低 / 適合性: 高 / 推奨判断: **採用済**(source_anchor_spec.md)

### A-3. 理解ノートのダイジェストを質問コンテキストへ注入
- 解決する問題: LLMがユーザーの現在の理解水準を知らず、毎回ゼロから説明する
- 差分: 要件§9の「既に蓄積された理解ノート」を、全文でなく直近12項目の1行ダイジェストとして実装(コスト制御)
- 期待効果: 読み進めるほど回答が文脈化する=「ノートが育つ」体験の中核
- コスト: 小 / リスク: 低 / 推奨判断: **採用済**

### A-4. 保存先提案APIの非ブロッキング設計
- 解決する問題: LLM提案待ち・失敗が保存操作(§22.4)をブロックする
- 提案: ヒューリスティック即答を基本、LLM提案は来たら上書き。suggest APIは5xxを返さない
- 期待効果: 保存は常に2クリックで完了 / コスト: 小 / 推奨判断: **採用済**

### A-5. 初期抽出のヒューリスティックフォールバック
- 解決する問題: LLMのJSON出力失敗・キー未設定で登録フローが死ぬ
- 提案: 失敗時は見出し構成+冒頭段落からの機械抽出に自動フォールバックし、その旨を明記
- 期待効果: 登録が絶対に完了する / コスト: 小 / 推奨判断: **採用済**

### A-6. 読書再開位置・ペイン状態の記憶(localStorage)
- 解決する問題: 再訪時に毎回先頭から
- コスト: 極小 / 推奨判断: **採用済**(サーバー正本原則の例外として表示状態のみ)

## B. MVP後すぐに追加を推奨

### B-1. DOI / arXiv APIによるメタデータ補完
- 解決する問題: PDFメタデータは欠損が多く書誌が不正確
- 提案: 登録時に検出したDOI→Crossref、arXiv ID→arXiv APIで著者・年・タイトルを補完(確認UI付き)
- コスト: 小 / リスク: 外部API依存(失敗しても登録は成立させる) / 判断: MVP後すぐ

### B-2. ストリーミング回答
- 解決する問題: 長い回答で10秒以上の無応答待ち
- コスト: 中(SSE+3プロバイダー対応) / 判断: MVP後すぐ(体感品質に直結)

### B-3. Obsidian/ローカルVaultへの自動エクスポート
- 提案: 設定でディレクトリ指定→ノート更新時にexport.mdを自動書き出し
- コスト: 小 / 判断: MVP後すぐ(§18の接続先第一号として最小コスト)

### B-4. タスク別モデル設定
- 提案: 翻訳=安価モデル、批判的検討=高性能モデル、のようにconfigでタスク別指定
- コスト: 小(設定構造は拡張可能に設計済み) / 判断: MVP後すぐ(コスト最適化)
