# 設計思想 — Reading Workspace

このドキュメントは、本ツールが **なぜこの形になっているか** と、改良するときに **何を守り、何を変えて良いか** を説明します。実装の詳細は `design.md` を、要件は `requirements.md` を参照してください。

このドキュメントは **改良に着手する前に必ず読んでください**。ここに書かれた「不変条件」と「6原則」を理解しないままの改良は、ほぼ確実にツールを別物へ変質させます。

---

## 1. このツールが解こうとしている一つの問題

> **AIに要約させると理解した気になるが、後から使える形では何も残らない。**

論文・技術記事・研究資料を LLM に読ませる体験は、
一度のセッションで完結してしまい、後から次の3つが得られません:

1. **どこに書かれていたかへ戻る道**(根拠原文への復帰)
2. **有益だった説明を選んで残す仕組み**(選択的保存)
3. **自分の理解が育っていく感覚**(資料単位の永続的な理解ノート)

本ツールは、上記の3つを **同一 UI 内・同一データ構造の中で** 満たすことだけを目的として作られています。要約もチャットも翻訳もPDFビューアーも、そのための **手段** です。

## 2. プロダクト思想 — 5つの中核信念

これは主観の表明ではなく、設計判断の判定基準です。改良提案がこれらに反する場合、その改良は本ツールの目的から外れています。

### 2.1 資料が中心単位である(チャットではなく)

一般的な LLM ツールは **会話スレッド** を中心単位とし、資料はそれに添付されるものと扱います。本ツールはこれを反転させ、**資料** を情報管理の中心単位とし、対話・メモ・知識はすべて資料に従属します。

- 影響: 「チャット履歴一覧」画面は存在しない。同じ資料を再度開いても新しいスレッドは作られず、既存の理解ページの続きが開く
- 判定基準: 「対話単位で何かを一覧・検索したい」という改良案が来たら、それは資料単位で表現できないかをまず問うべき

### 2.2 保存するかどうかはユーザーが決める(自動保存しない)

LLM が生成したすべての回答を自動でノートに追加すると、ノートは短時間で無価値な情報の集積になります。本ツールは、ユーザーが「これは残したい」と感じたものだけを、ワンクリック級の操作で保存します。

- 影響: 「毎回のQ&Aを全部残す」機能は絶対に追加してはいけない
- 判定基準: 「AIがこの回答は重要と判定して自動保存する」提案は却下。ただし「AIが保存を提案する UI ヒント」は歓迎

### 2.3 原文と AI の出力は絶対に混ぜない

保存された知識項目には常に **origin**(source_quote / auto_extract / llm / llm_edited / user)と **info_type**(fact / claim / result / llm_summary / llm_interpretation / user_thought / open_question / idea / term / action / translation)が付随します。UI ではバッジ色で、エクスポート Markdown ではラベル文字列で、この区別が保たれます。

- 影響: 「見た目のノイズになるからバッジを消したい」という改良は却下。折りたたみは可
- 判定基準: 保存経路を新設するなら origin と info_type の付与が必須

### 2.4 常に原文に戻れる

保存された知識項目、質問、回答、ハイライトはすべて **SourceAnchor** を持ち、原文の該当位置へ戻れます。アンカーは単一方式に依存せず、**blockId → blockIdx+quote → quote 全文検索 → page** の 5 段階でフォールバックします(詳細は `design.md`)。

- 影響: 資料の再解析やWebページ更新後も、リンク切れではなく「近傍発見」で成立させる
- 判定基準: 新しい保存経路には必ずアンカーを付ける。付けられない場合はその理由を残す

### 2.5 データはユーザーのものであり、外に持ち出せる

すべての知識は SQLite と平文 Markdown / JSON でエクスポートできます。本ツールが利用できなくなっても、蓄積された知識は Obsidian でも他のエディタでも読める形で残ります。

- 影響: 独自バイナリ形式・専有クラウド保存・エクスポート不能なフィールドは追加しない
- 判定基準: DB スキーマに新しい列を足したら、その列は必ず `export.md` か `export.json` のどちらかに現れる

## 3. 何ではないか(明示的な非目標)

改良過程で「これも足せるのでは」という誘惑が繰り返し訪れます。以下は **意図的に含まれていないもの** です。追加を提案する前に、なぜ今含まれていないのかを理解してください。

| 非目標 | 理由 |
|--------|------|
| チャットボット | 対話は資料に対して行うものであり、対話自体を管理する対象ではない |
| 万能ノートアプリ | ノートは資料に紐づくもの。資料に紐づかない自由ノートは他のツール(Obsidian等)の役割 |
| 論文検索 / 発見 | 資料は登録済み前提。Semantic Scholar のような発見機能は本ツールの外 |
| 引用管理システム | Zotero と競合しない。BibTeX 生成は非目標 |
| 複数ユーザー共同編集 | ローカルファースト・単一ユーザー前提 |
| クラウドサービス | 全データがローカル SQLite にあることが本ツールの信頼性の根拠 |
| リアルタイム学習・パーソナライゼーション | LLM への入力は毎回明示的なコンテキスト(選択・前後・見出し・ノートダイジェスト)。暗黙学習しない |
| 特定 LLM プロバイダーへの深い最適化 | プロバイダーは交換可能な部品。どれか一つに賭けない |

## 4. 不変条件(改良で決して壊してはいけないこと)

**改良の際、以下は変更禁止です。** 変更が必要と思う場合、変更ではなく **拡張** で表現できないかをまず検討してください。それでも変更が不可避なら、`spec/` 全体を書き換える大改訂として扱ってください。

### 4.1 データレベルの不変条件

- **I-1**: すべての `knowledge_items` レコードは `origin` と `info_type` を必ず持つ
- **I-2**: `origin = 'auto_extract'` の項目のみ、初期抽出の再実行で削除・置換される。それ以外の origin の項目を自動処理が書き換えることは禁止
- **I-3**: `origin = 'llm'` の項目の `content` をユーザーが編集した場合、`origin` は自動的に `llm_edited` に遷移する
- **I-4**: すべての保存経路は `SourceAnchor`(または明示的な null)を受け取る
- **I-5**: DB スキーマ変更は破壊的でない(追加列は許容、既存列の型変更・削除は要マイグレーション設計)

### 4.2 LLM 利用の不変条件

- **I-6**: LLM への入力(system・user プロンプト・使用モデル・使用プロンプトID・使用コンテキストの要約)は必ず `answers.context_summary` に記録される
- **I-7**: LLM プロバイダーは `LLMProvider` 抽象を経由してのみ呼ばれる。ルートやビジネスロジックからプロバイダー SDK を直接呼ぶことは禁止
- **I-8**: プロンプトは `prompts/*.md` に frontmatter (id, version) 付きで格納される。コード中のリテラル文字列としてプロンプト本文を書くことは禁止
- **I-9**: `mock` プロバイダーが選択されている場合、実 LLM を必要とする機能はすべて動作する(ヒューリスティックフォールバックまたは明示的モック応答)。**mock でテストが通ることが CI の受け入れ基準**

### 4.3 UI の不変条件

- **I-10**: 質問・翻訳・保存の操作でページ全体の遷移(URL変更を伴う画面切替)を発生させない
- **I-11**: 資料本文の DOM 挿入は `textContent` のみ使用する(`innerHTML` 禁止)。LLM 出力の Markdown レンダリングだけ marked を使用する
- **I-12**: 表示状態(タブ選択・ペイン幅・スクロール位置)以外はクライアントに保存しない。サーバー(SQLite)が常に正本

### 4.4 契約の不変条件

- **I-13**: `/api/knowledge/suggest` は 5xx を返さない(常に heuristic 結果を返す)。この API のブロッキングが保存体験を壊すため
- **I-14**: `/api/meta` は LLM プロバイダーの初期化を要しない(API キーが無い状態でも 200 を返す)
- **I-15**: 資料登録エンドポイントは、重複を検出した場合、勝手に登録するのではなく `duplicate: true` を返してユーザーの判断を求める

## 5. 改良時の6原則

Kiro および人間の第三者開発者が、本ツールを改良する際の意思決定原則です。

### 原則 1 — 拡張ポイント優先

改良を実装コードの深部に足す前に、`design.md` の「拡張ポイント」節を確認してください。多くの改良は、以下の追加だけで実現できます:

- 新しい LLM プロバイダー: `app/llm/<provider>.py` を1ファイル追加
- 新しい資料タイプ: `app/ingest/<type>.py` を1ファイル追加
- 新しいプロンプト: `prompts/<id>.md` を1ファイル追加
- 新しい保存先セクション: `config/app.config.json` の `note_template` を編集
- 新しい prompt_type: `app/routes_qa.py` の PROMPT_TYPE_PREFIX と `app/main.py` の PROMPT_TYPES を編集

### 原則 2 — 契約とデータの二重更新

以下は**同時に**変更しなければなりません:

| コード変更 | 同時に更新するドキュメント |
|-----------|---------------------------|
| DB スキーマ (`app/db.py`) | `spec/design.md` データモデル節 |
| API シグネチャ (`app/routes_*.py`) | `spec/api_reference.md` |
| 新しい origin / info_type 値 | `spec/design.md` の語彙表 + `spec/requirements.md` |
| プロンプト本文 | 該当 `prompts/*.md` の frontmatter version を +1 |
| 拡張ポイントの契約 | `spec/design.md` の「拡張ポイント」節 |

契約とデータのどちらかだけが更新されている PR は不完全とみなしてください。

### 原則 3 — オフライン動作を壊さない

すべての改良は、`mock` プロバイダーで動作させたときに UI が壊れず、既存の pytest が通る状態でマージされなければなりません。API キーを前提とする機能を追加する場合、mock 側の代替挙動(ヒューリスティック / モック応答)を必ず用意してください。

### 原則 4 — ノート育成体験を壊さない

「保存操作を2クリックで完了」「読書中に画面遷移が起きない」「原文が常に近い」— これらが本ツールの体験の核です。改良で画面遷移や追加ダイアログを増やす場合、その改良は本当に体験を良くするかを問うてください。多くの場合、答えは No です。

### 原則 5 — LLM 出力を事実として扱わない

新機能で LLM 出力を扱う場合、それが `fact` として保存されることは絶対に許可しないでください。デフォルトは `llm_summary` か `llm_interpretation` です。ユーザーが「事実として確認した」と明示的に verification を上げた場合のみ、事実に近い扱いが可能になります。

### 原則 6 — 移植可能性を維持する

本ツールは他のシステムに **切り出して組み込まれる** ことを想定しています。以下の依存を新たに増やさないでください:

- OS 固有機能への依存(Windows レジストリ、macOS ショートカット等)
- Node.js / npm ツールチェーンへの依存(フロントエンドはビルド不要のまま)
- グローバル状態(モジュール変数によるキャッシュは最小限)
- 特定 GPU / ハードウェアへの依存

新しい pip 依存を追加する場合、pure Python または広く配布されている wheel があるものに限ります。

## 6. 「良い改良」と「悪い改良」の見分け方

| 改良提案 | 良い / 悪い | 理由 |
|---------|-------------|------|
| ストリーミング応答を追加 | 良 | 体験の質を上げ、既存契約を壊さない |
| Ollama で動く openai_compat のドキュメント整備 | 良 | 拡張ポイントの活用、プロバイダー非依存原則の強化 |
| 保存時にタグ候補を LLM から取る | 良 | suggest と同型の non-blocking パターンで実装可能 |
| 全 LLM 回答をノートに自動追加 | **悪** | 2.2 に真っ向から反する |
| 資料単位ではなくトピック単位に情報を集約 | **悪** | 2.1 に反する。将来の「知識横断ビュー」は別レイヤーとして追加すべき |
| origin バッジを UI から削除 | **悪** | 2.3 に反する |
| DB を PostgreSQL 前提に変更 | **悪** | 移植可能性・ローカルファーストを壊す。オプションとしての追加は可 |
| Anthropic SDK に依存 | **悪** | I-7 に反する。httpx 直呼び出しの方針は維持 |
| PDF 表示を独自レンダラで置き換え | 要検討 | pdf.js より軽量・高精度な選択肢があれば可。ただしテキスト選択とアンカー生成の契約を破らないこと |
| 意味検索 (embedding) を追加 | 良(条件付き) | 既存の LIKE 検索エンドポイントを **置換** ではなく **並存** させ、ローカル動作のフォールバックを残すこと |

## 7. 変更のドキュメント化

改良を加える際、以下を必ず追加してください:

1. `spec/tasks.md` に完了したタスクをチェックし、次のタスクを追加
2. 破壊的な変更、または将来の意思決定に影響する変更を行った場合、`spec/decisions/ADR-<番号>-<slug>.md` を新規作成(ADR ディレクトリが存在しなければ作成)
3. 契約の変更は原則 2 に従い spec を同時更新

Kiro が spec-driven モードで動く場合、これらは自動的に規約化されているため、通常のワークフローで満たされます。

## 8. なぜこの思想文書を分離したか

技術設計 (`design.md`) を読んだだけでは、なぜその設計なのかが分かりません。理由を知らないままの改良は、必ず「もっと便利にした」と言いながら本ツールの目的を壊します。

この文書はそれを防ぐために存在します。**あなた(改良する開発者 / Kiro)が「この改良は 2.x や I-y に反する」と気づけたなら、この文書は仕事をしています。**
