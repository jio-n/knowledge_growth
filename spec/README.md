# Reading Workspace — 仕様書 / 設計書パッケージ

このディレクトリは、`knowledge_growth`(以下「本ツール」)を **他のシステムへ組み込む**、あるいは **改良するコーディングエージェント(Kiro など)や第三者開発者が読むためだけの独立したパッケージ**です。

- 本ツールの内部リポジトリ(`docs/` 配下)を読まなくても、この `spec/` だけで組み込み・改良を開始できます
- 想定読者: 本ツールに関する前提知識・研究開発の背景を **一切持たない** 開発者、およびコーディングエージェント Kiro
- 想定作業: (1) 本ツールを別リポジトリへ切り出して移植する / (2) 移植先で改良する / (3) 既存FastAPI を HTTP 経由で外部システムから呼び出す

## 本ツールを一言で

> **資料(PDF・Webページ・テキスト・Markdown)を読み、原文を確認しながらLLMに質問し、"残したい知識だけ" を資料ごとの理解ノートへ保存・蓄積する、ローカルファーストの読解ワークスペース。**

チャットボットでも、要約ツールでも、PDFビューアーでもありません。**資料が情報管理の中心単位**であり、原文・翻訳・LLM対話・ユーザーメモ・出所付き知識項目が同一資料に紐づいて **育っていく** ことを可能にする「読解の器」です。

## 読む順番(必ずこの順で読んでください)

| # | ファイル | 内容 | 分量目安 |
|---|---------|------|---------|
| 1 | [design_philosophy.md](design_philosophy.md) | **設計思想と改良時の原則**。何のために作られ、何が不変で、何を変えて良いか。**改良に着手する前に必ず読む** | 中 |
| 2 | [requirements.md](requirements.md) | **Kiro spec 準拠(EARS 記法)** の要件。受け入れ基準の正本 | 中 |
| 3 | [design.md](design.md) | **Kiro spec 準拠**の技術設計。構造・データフロー・拡張ポイント | 大 |
| 4 | [api_reference.md](api_reference.md) | **REST API 完全仕様**。外部から呼ぶ / 移植する際の中核契約 | 大 |
| 5 | [tasks.md](tasks.md) | **Kiro spec 準拠**の改良タスク雛形。着手候補のチェックリスト | 中 |

`design_philosophy.md` → `requirements.md` → `design.md` の順は特に重要です。順番を飛ばすと、なぜその設計になっているかが分からず、悪い改良を入れる危険があります(詳細は design_philosophy.md 「改良時の6原則」参照)。

## このパッケージの範囲

**含むもの**:
- 本ツールが何であり、何でないか
- ユーザーが得る体験と、それを支えるデータ構造・API・LLM扱いの契約
- 拡張ポイント(LLMプロバイダー追加、資料タイプ追加、プロンプト、保存先セクション等)
- 改良時に守るべき不変条件と、破ってはいけない設計判断

**含まないもの**:
- 本ツールが元々どのような研究プロジェクトの中で使われていたか
- ユーザー個人のワークフローや業務文脈
- 実装コードの逐行解説(コードそのものと、この spec の対応関係で読み解いてください)

## 改良を始める前のチェックリスト

- [ ] `design_philosophy.md` を読み、「不変条件」節を理解した
- [ ] `requirements.md` の受け入れ基準のうち、改良で **維持** すべきものを把握した
- [ ] `design.md` の「拡張ポイント」節を読み、改良が既存の拡張点で表現できないか確認した
- [ ] 変更する API があれば `api_reference.md` の該当エンドポイントを同時に更新する予定になっている
- [ ] 変更するデータ形状があれば `design.md` の「データモデル」節を同時に更新する予定になっている

## 用語の凡例

- **資料 (Source / ResearchSource)**: PDF・Webページ・テキスト・Markdown を等しく扱う上位概念
- **ブロック (Block)**: 抽出後の資料本文を構成する順序付きの意味単位(見出し・段落・コード・引用・リスト・表・図キャプション)
- **アンカー (SourceAnchor)**: 知識・質問・回答から原文位置へ戻るための冗長識別子
- **知識項目 (KnowledgeItem)**: ユーザーが「残したい」と選んで保存した情報の最小単位。出所と情報種別を必ず持つ
- **理解ノート (Understanding Note)**: 資料ごとに1つ存在する「生きた文書」。実体は知識項目のセクション別ビュー(独立文書としては保存されない)
- **オフラインモック (mock provider)**: APIキーなしで全機能を動作させるためのダミー LLM。回答には必ずモック識別子が付き、実回答と誤認できない
